# Evaluating SentinelOps

An incident agent can sound convincing while naming the wrong cause or recommending a dangerous tool. Evaluation turns those behaviors into reviewable measurements. The supplied numbers are generated by running code; the repository does not assume target scores.

## 1. Freeze the questions before measuring the answers

`evals/incidents.json` contains 64 synthetic incidents: 16 release-related failures, 16 memory-growth incidents, 16 saturated database pools, and 16 ambiguous or healthy observations. They cover eight service names and different error rates, release ages, resource pressures, connection limits, misleading historical releases, and hostile log text.

Each fixture contains two sections:

| Section | Contents | Who receives it |
|---|---|---|
| `input` | Service, description, explicit metrics/deployments/logs/database observations | Investigation workflow |
| `expected` | Root cause, relevant evidence sources and runbook IDs, allowed read tools, forbidden tools, recommendation, approval requirement | Evaluator only |

Every input has `scenario: "unknown"`. This matters: passing a cause-specific scenario such as `memory_leak` to the classifier would give it the answer. The fixture tools expose the supplied observations; the classifier must derive its answer from those observations. `workflow_input()` enforces the accepted input fields and rejects a non-neutral scenario.

`evals/build_fixtures.py` reconstructs the checked-in JSON from explicit observation rows. Review the JSON, freeze it for a comparison, and change its version deliberately when you change the benchmark. The report records its SHA-256 hash so two runs can be compared against the same data.

These are integration fixtures designed alongside the rule baseline. They are useful regression checks, but they are not an independent test set proving generalization to real incidents.

## 2. Run the real workflow

From the repository root, install the backend and run:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -e 'apps/api[dev]'
cd apps/api
python -m sentinelops.evaluate --output ../../evals/results/latest.json
```

The harness calls `sentinelops.workflow.investigate_case()` for every case, with fixture adapters and real orchestration/retrieval/policy code. It records wall-clock duration using a monotonic clock. A case that raises an exception stays in the denominator and scores zero on the correctness checks; it is not silently excluded.

The default `--mode fixture` avoids network calls and API credentials. Its output identifies itself as `deterministic_fixture_baseline`. A high score means that the rules and their integration handle these observations; it does not mean an OpenAI model has that accuracy.

For a separate, explicitly billed live-model run, configure `OPENAI_API_KEY` and `OPENAI_MODEL`, then run:

```bash
python -m sentinelops.evaluate --mode openai --output ../../evals/results/openai.json
```

This still uses synthetic telemetry. Keep the output separate from `latest.json` and compare it with the deterministic baseline. A live-model request or parsing failure counts as an error; the evaluator must not relabel a fixture fallback as a measured live-model result. The interface and code should be inspected before sending real incident data to an external model.

## 3. Understand exactly what each metric measures

| Metric | Formula / observation | Practical meaning |
|---|---|---|
| Root-cause accuracy | Correct expected root labels / all 64 cases | Correctness within the four supplied categories |
| Retrieval Recall@5 | Mean of relevant expected runbooks found among the first five results / expected relevant runbooks | Whether the relevant seeded runbook was available |
| Evidence coverage | Mean of expected evidence source types present / expected source types | Whether required types of evidence were gathered |
| Tool-selection accuracy | Expected mutation tool equals proposed mutation tool, including `null` / all cases | Whether the action recommendation is appropriate for the fixture |
| Read-tool policy adherence | All recorded investigation calls use validated accepted read tools / all cases | Whether investigation remained inside the read boundary |
| Unsafe-action rejection | Rejected hostile tool inputs / hostile tool probes | Allowlist and argument validation behavior |
| Approval-policy adherence | Correct fixture approval gates plus denied unauthorized execution probes / both groups combined | Proposal gates and independent authorization rechecks |
| Accepted-control accuracy | Valid calls accepted / valid controls | Detects a broken policy that rejects everything |
| Latency P50/P95 | Nearest-rank percentiles of local per-case wall time | Repeatable local investigation overhead, subject to host load |

Approval-policy adherence combines two different kinds of checks. The report preserves per-case outcomes and individual policy probes so a reviewer can inspect their denominators separately. Safety probes include unknown tools, write/delete tools, raw SQL, extra fields, invalid template names, wrong roles, missing/expired approvals, changed tool arguments, changed fingerprints, and changed bound idempotency keys.

The report deliberately sets `successful_remediation` and `average_llm_cost_usd` to `null`: this harness stops at the approval gate and does not collect provider billing or execute approved remediations. Demo remediation and verification are exercised in the lifecycle tests. Their success is simulator behavior, not a production recovery rate.

Several tempting interpretations are incorrect:

- Source presence does not prove that the explanation accurately cites its evidence. Add human or structured evidence-grounding review for that.
- Retrieving among four runbooks can yield generous Recall@5. Evaluate a larger, distractor-rich collection before selecting a production retrieval strategy.
- Rule-generated confidence is not calibrated probability. Do not display it as a measured likelihood of correctness.
- Local fixture latency does not include real telemetry providers, network queues, model calls, or customer database performance.
- One adversarial log example does not establish resistance to all prompt injections. Maintain an expanding attack suite and keep policy enforcement outside the model.

## 4. Verify the full human approval lifecycle

From the repository root:

```bash
python -m pytest tests apps/api/tests
```

The tests call FastAPI through its test client, use a temporary SQLite database, and drain queued jobs explicitly. No production system is contacted. Their purpose is to check boundaries that a workflow-only score cannot see: unauthenticated requests, wrong roles, execution before approval, rejected proposals, fingerprints changed after approval, duplicate idempotency keys, and simulated verification failure.

The policy unit tests also check strict typed arguments and named read-only query templates. A read-only string beginning with `SELECT` is not sufficient protection: it could still expose data or contain unsafe SQL. SentinelOps instead accepts adapter-owned template names and rejects SQL strings entirely.

## 5. Add stronger evaluation before customer use

Begin with anonymized historical incidents reviewed by operators. Include incidents the agent should refuse to diagnose, missing telemetry, competing hypotheses, contradictory evidence, stale runbooks, compromised logs, and provider outages. Keep development and holdout sets separate. Record the model, prompt, tool schemas, retrieval version, and dataset hash with each run.

Next, test model calls with real usage records so token count and cost are measurable. Add calibrated confidence and evidence-grounding review, and measure a complete approved remediation in a controlled staging system. Successful recovery should mean the system stayed healthy for a defined observation window, not simply that a mutation API returned 200.

Finally, set release gates appropriate to the customer. Safety failures should block a release. Accuracy thresholds need a baseline, a representative held-out dataset, and an explicit tolerance for abstaining. The included CI gates validate this implementation and its fixtures; they do not certify production readiness.
